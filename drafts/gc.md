%% "Fine, we get it why are you harping on this so much?", great question! Because this distinction was key to addressing one of the top 3 hardest things I have had to debug (perhaps a separate post!). The TL;DR is we were experiencing some truly baffling behavior in production. The proximate cause was finalizers on certain objects never running. Critically, a particular data structure's correctness depended on these finalizers running to completion. The data structure would silently end up corrupted leading to all sorts of fun outcomes. The discussion around what to do was very interesting. The immediate reaction was to instrument some detection of the finalizer not running, and try to bring the process to a healthy state or just crash and restart it. Doing either of this would have been really bad! The proximate cause did not explain the fundamental nature of the failure! The acute reader might be asking "but why did the finalizers not run?". The answer is the process's stack overflowed at **just** the right (wrong?) time -- _during_ garbage collection. Moreover, the system **assumed** that all stack overflows are recoverable errors and leave the system in a valid state. Hence, it would just catch the exception, fail the user's request, and keep processing new requests. You can probably see where this is going. First: A (in-process, in-thread, non-concurrent) garbage collector's contract can be thought of as "assuming a valid starting state, after running to completion, dead objects will be collected and no live objects will be collected" or something along those lines. But this says nothing about GC not running to completion! Second: stack overflows can happen absolutely *anywhere*, including during GC! Putting these two together, we can classify stack overflows as being a failure: you may assume nothing about the state of the system when one happens. Trying to bring the system back to a healthy state when you know nothing about the correctness of memory is basically fatal.
